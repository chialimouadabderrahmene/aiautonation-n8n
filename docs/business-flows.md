# Business Flows — trigger → eligibility → recipient → channel → message → time → delivery → stop rule → outcome

Two separate automation systems exist. **Do not confuse them:**

| System | Where it lives | Channels | Runs |
|---|---|---|---|
| **A. n8n launch/acquisition automation** (this repo, `n8n-workflows/`) | n8n on Railway | WhatsApp Cloud API (templates), Resend email, Telegram (team), ManyChat DM reply | see per-workflow schedule (Africa/Lagos) |
| **B. In-app lifecycle automations** (`ekiapp-backend-main/src/modules/automation`) | Eki backend (Vercel) | push + in-app (+ email for low stock) | one daily Vercel cron, 12:00 UTC |

System B has **no n8n and no WhatsApp integration** (`grep` finds no n8n/WhatsApp code in the backend automation module). Requests such as "first sale, cart recovery, win-back, review request, low stock, referral, smart reorder, renewal, failed-payment recovery, Community Buy events" are System B — documented in §B from the source code. What was verified for each system is stated in each section.

## A. n8n workflows (22 files: `00` error handler + the 21 original numbers; there is no workflow 11)

Legend — **WA template** = WhatsApp message template that must be approved in WhatsApp Manager first (**EXTERNAL DEPENDENCY**; proposed texts in [whatsapp-templates.md](whatsapp-templates.md)). If the template name env var is empty the step is **blocked** (nothing is sent; one Telegram alert per run).

Global stop rules for every WhatsApp send in A: lead must have `opt_in=yes`, empty `opt_out_at`, status not `unsubscribed`/`converted`/`churned`, valid phone (8–15 digits). `STOP` (also `unsubscribe, quit, cancel, opt out, optout, basta, stop all`) sent to the number persists `status=unsubscribed`, `opt_in=no`, `opt_out_at`; `START` re-subscribes. One lead per loop iteration, so a failing lead never causes other leads to be re-sent.

## B. In-app lifecycle automations (backend, from source — `src/modules/automation/*`, `regular-deliveries/renewals.service.ts`, `community-buy/community-campaigns.service.ts`)

Common rules (`automation.service.ts`): quiet hours **22:00–07:00 UTC** (run skipped, retried on the next sweep); recipient must exist and not be suspended; `requiresMarketingConsent` types need `User.marketingConsentAt`; vendor-level toggle (`VendorAutomationSetting`, default enabled); per-type frequency cap; DB-unique `dedupeKey` (`type:subjectKey`) guarantees one message per subject. Delivery goes through `communicationService.send` → push + in-app (email only for low stock); per-channel failures are logged, not retried by a queue. The whole sweep runs from one daily Vercel cron (`0 12 * * *` UTC → `/api/internal/jobs/daily-sweep`).

**Verified by me:** `npx vitest run` in `ekiapp-backend-main` for `automation-detectors`, `automation`, `automation-routes` (45 tests), and `regular-deliveries-renewals`, `notifications-dedupe`, `community-buy` (293 tests): **338 passed**. These are unit/integration tests with mocked providers — they prove eligibility, dedupe and consent logic, **not** that a real push/email reached a device. Quiet-hours risk: a sweep executed at 12:00 UTC is outside the 22:00–07:00 window, so messages are sent; user-local time is not considered (documented backend limitation).
